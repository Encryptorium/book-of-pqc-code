SLH-DSA implementation for Chapter 17 of the Encryptorium Book of Post-Quantum Cryptography. `adrs.py` is the 32-byte address structure and its 22-byte compressed form; `tweakable.py` instantiates the six hash functions for both the SHA2 and SHAKE families; `wots.py`, `fors.py` and `hypertree.py` build the three components; `slh.py` assembles them. `params.py` carries all twelve FIPS 205 parameter sets. Standard library only (`hashlib`, `hmac`, `struct`, `os`, `dataclasses`); no external dependencies.

Unlike the Chapter 16 package, this one targets the standard itself rather than a teaching variant. `pytest tests/ch17` checks it against the official NIST ACVP vectors: key generation byte for byte at all twelve parameter sets, signature verification accepting a valid case at all twelve, and signature generation byte for byte at the six `f` sets. The committed verification fixture carries the invalid cases at two parameter sets only, SLH-DSA-SHA2-128s and SLH-DSA-SHAKE-128s, six rejection reasons apiece; the other ten groups carry no invalid case and so reject nothing. The divergences below are what remains.

**Only the internal interface is implemented, and one function name is a trap.** FIPS 205 Section 10 wraps the internal algorithms in `slh_sign` (Algorithm 22), `hash_slh_sign` (Algorithm 23), `slh_verify` (Algorithm 24) and `hash_slh_verify` (Algorithm 25), each of which prefixes a domain separator and a caller-supplied context string, and in the pre-hash case an OID, before the internal signer sees the message. None of those four is implemented here. **The `slh_sign` and `slh_verify` exported by this package are not FIPS 205's `slh_sign` and `slh_verify`.** They take no `ctx` argument and prefix nothing; `slh_sign` is a convenience wrapper that picks `opt_rand` and calls `slh_sign_internal` (Algorithm 19): `os.urandom(n)` by default, the hedged variant, or PK.seed when called with `randomize=False`, the deterministic variant. `slh_verify` is Algorithm 20. A signature produced here will not verify against a conforming implementation driven through the external interface, and vice versa.

**No side-channel or fault hardening.** FIPS 205 Section 3.2 says that "care must be taken to protect implementations against attacks, such as side-channel attacks or fault attacks". Nothing here does. Chain lengths in `wots_sign` depend on the message digits, which is the timing leak Chapter 18 describes, and the verify-after-sign countermeasure it recommends is not implemented. Comparisons are ordinary Python `==` and are not constant-time.

**No key checks.** FIPS 205 Section 3.1 requires, where public-key validation is required, a check that the public key is $2n$ bytes long. Where possession of the private key is assured by regenerating it, the owner must check that the private key is $4n$ bytes and recompute PK.root from SK.seed and PK.seed against the stored value. Nothing here does either. `slh_verify` reads PK.seed and PK.root from the first $2n$ bytes of the key and ignores any bytes after them, so it accepts a longer key, and no function checks a stored private key against its PK.root.

**Passing the ACVP vectors is not validation.** These are the public test vectors from the NIST ACVP-Server repository, run offline against committed fixtures. This is not a CMVP-validated cryptographic module, and nothing here has been reviewed for production use.

**Randomness.** `slh_keygen` draws SK.seed, SK.prf and PK.seed from `os.urandom`, and `slh_sign` draws `opt_rand` from the same source, which is the hedged variant. FIPS 205 requires those three key-generation values to come from an approved random bit generator supporting at least $8n$ bits of security strength (Sections 3.1 and 10.1), and `os.urandom` is the platform CSPRNG, not such an approved generator. It asks less of the hedged variant's random value, which it calls addrnd and passes as `opt_rand`: addrnd "should ideally be generated by an approved random bit generator, other methods for generating fresh random values may be used" (Section 9.2).

The package exists to be read and rebuilt rather than deployed. `exercises/ch17-slh-dsa` is the same package with 25 of its functions replaced by stubs. The ones the chapter prints in full arrive already implemented, so the rebuild track never asks anyone to retype the page: the ADRS setters and its keypair getter, its compressed form, the WOTS+ public-key routine, and the XMSS node recursion. What is stubbed is what the chapter explains but does not print, which includes the tweakable hashes at their SHAKE and SHA-512 branches.
